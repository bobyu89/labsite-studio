## 一、該參考誰、參考什麼

從上次找到的專案裡，只留下五個，每個只借一件事。其餘略過。

| 排序 | 專案 | 授權 | 借什麼 | 怎麼用 |
|---|---|---|---|---|
| 1 | **Pages CMS** https://github.com/pages-cms/pages-cms | MIT | **上雲的整套藍本**：Next.js + PostgreSQL + Drizzle ORM + GitHub App + Better Auth，有自架版與託管版（app.pagescms.org） | Phase 2 的後端骨架直接照它的資料表與 GitHub App 流程設計，不用從零想 |
| 2 | **Sveltia CMS** + **sveltia-cms-auth** https://github.com/sveltia/sveltia-cms-auth | MIT | (a) Worker 的 `ALLOWED_DOMAINS` 白名單與 PKCE；(b) GitHub API 讀寫層（GraphQL 批次讀、Git Trees 多檔 commit）；(c) i18n 並排編輯 UI | Phase 0 補 Worker 安全；Phase 1 抄 commit 流程；v3.2 雙語 UI 對照改進 |
| 3 | **CloudCannon**（商業）https://cloudcannon.com/documentation/articles/introducing-the-visual-editor/ | 閉源 | 只看文件：`data-editable` / `data-path` / `data-key` 標記慣例，以及「視覺編輯 + 代管」的產品定位與定價 | 把你的 `data-ls` 規則寫成公開文件；Phase 3 商業模式對照 |
| 4 | **Greene Lab lab-website-template** https://github.com/greenelab/lab-website-template 及其他 Jekyll 實驗室模板 | BSD-3 | 當**測試語料與目標用戶**，不是借程式碼 | 用它們的 `_site/` 產物跑 round-trip 測試；未來若支援 Jekyll 站點的第一批對象 |
| 5 | **GrapesJS** https://github.com/GrapesJS/grapesjs | BSD-3 | 只借拖拉 UX 細節（拖曳中的佔位、區塊 hover 高亮、鍵盤操作） | 反面教材：官方明說 HTML 不能當持久層，證明你的「原格式映射表」是正確方向，README 可引用這點 |

**不參考的與原因**
- Silex、VvvebJs：都是「從零建站」的 builder，會重寫整份 HTML，與你的核心價值（改原檔、diff 最小）相反。
- Onlook：目標是 React 原始碼，領域不同。
- Sitecake：需要 PHP 後端且核心閉源，只有 `sc-content` 標記概念，CloudCannon 已涵蓋。
- Decap CMS、Keystatic、JekyllPad、Sitepins：都依賴 SSG 與 schema，且 JekyllPad / Sitepins 非完全開源。

## 二、你的差異化定位（先寫進 README）

一句話：**不需要 SSG、不需要 schema 設定檔、直接開現成的靜態 HTML 改內容，寫回時 git diff 只有你改的那幾行。**

市面上沒有開源專案同時做到這四點。上雲之後這句話也是產品的主賣點，不要在加後端的過程中把它弄丟。

## 三、階段計畫

### Phase 0：把現在的版本補到「可以交給別人用」（約 2 週）

目標：關掉 VALIDATION.md 裡列出的已知缺口，維持純前端架構不變。

1. **Worker 安全補強**（參考 sveltia-cms-auth）
   - 加 `ALLOWED_DOMAINS` 環境變數，只允許你的 GitHub Pages 網域拿 token。
   - OAuth 流程加 `state` 參數防 CSRF；有餘力再加 PKCE。
   - Worker 回傳 token 改用 `postMessage` 到指定 origin，不要放在 URL。
2. **GitHub 提交端到端測試**
   - 用一個測試 repo 跑：登入 → 開頁 → 改一個欄位 → 存檔 → 確認 commit 內容與 SHA 衝突偵測。
   - 把這個流程寫成 GitHub Actions 的整合測試（可用 GitHub App token 或 PAT secret）。
3. **瀏覽器相容**：Firefox、Safari 手動過一輪；File System Access API 在 Firefox / Safari 不可用，UI 要優雅降級（隱藏「開資料夾」，只留 GitHub 與網址）。
4. **README 加「與 Decap / Sveltia / Silex 的差異」段落**，並把 `data-ls` 標記規則獨立成 `docs/markup-convention.md`。
5. **測試語料擴充**：把 Greene Lab LWT 的 `_site/` 產物加進 round-trip 測試，看非你自己寫的 HTML 結構會不會爆。

交付物：v3.3 tag、VALIDATION.md 已知缺口清空。

### Phase 1：把 GitHub 發布流程做完整（約 4～6 週）

目標：讓不懂 git 的研究室成員能安全地「存草稿 → 送審 → 發布」。

1. **多檔一次 commit**：改用 Git Trees API（blob → tree → commit → ref），圖片與 HTML 同一個 commit，避免半套狀態。參考 Sveltia 的 GitHub backend 實作。
2. **編輯工作流（editorial workflow）**：
   - 存檔預設寫到 `labsite/draft-<user>` 分支並開 PR，而非直接 push `main`。
   - UI 顯示 PR 狀態；管理者可在 UI 內 merge。
   - 這一步是上雲後「審核」功能的前身，資料模型現在就先想好。
3. **Pages 部署狀態**：呼叫 Deployments / Pages API 顯示「已發布 / 建置中 / 失敗」。
4. **圖片處理**：上傳前在瀏覽器端壓縮與轉 WebP（可選），限制大小。
5. **衝突處理 UX**：SHA 不符時顯示三方差異（原檔 / 你的 / 遠端），至少要能「重新載入並保留我的修改」。

交付物：v4.0。到這裡為止仍是純前端 + 一支 Worker，零營運成本。

### Phase 2：上雲 MVP，加後端（約 2～3 個月）

**為什麼要加後端**：純前端版有四個做不到的事——(1) 沒有 GitHub 帳號的成員無法登入；(2) 草稿只在單一瀏覽器；(3) 沒有多人協作與審核紀錄；(4) 無法幫使用者代管網站。這四件事都需要資料庫與伺服器端身分。

**技術選型建議：Cloudflare 全家桶**

| 需求 | 選擇 | 理由 |
|---|---|---|
| 運算 | Cloudflare Workers（已有） | Worker 已存在，團隊已熟；免費額度每日 10 萬次請求 |
| 資料庫 | Cloudflare D1（SQLite）+ Drizzle ORM | 免費額度夠 MVP；Drizzle 與 Pages CMS 相同，schema 可直接對照 |
| 檔案 | Cloudflare R2 | 草稿圖片、暫存資產；無出口流量費 |
| 快取 / session | Cloudflare KV | session、GitHub API 回應快取 |
| 前端託管 | Cloudflare Pages | 取代 GitHub Pages，同一個帳號管理 |
| 身分 | GitHub App（取代 OAuth App）+ Email magic link | GitHub App 可只授權特定 repo、權限細粒度；Email 給沒 GitHub 的成員 |
| 框架 | 保留 React + Vite 前端；後端用 Hono on Workers | 不必搬到 Next.js；Hono 輕量、與 Workers 原生相容 |

**替代方案**：完全照 Pages CMS 走 Next.js + PostgreSQL（Neon / Supabase）+ Vercel。優點是可以幾乎直接參考它的程式碼；缺點是要把前端從 Vite 搬到 Next.js，且多一家供應商。若你未來想大量借用 Pages CMS 程式碼，選這條；否則選 Cloudflare。

**MVP 功能範圍**
1. 帳號：GitHub App 登入、Email magic link 登入、一個使用者可屬於多個「工作區」（實驗室）。
2. 工作區：綁定一個或多個 GitHub repo；角色分 owner / editor / viewer。
3. 草稿雲端同步：IndexedDB 草稿改為「本機先寫、背景同步到 D1」，斷線可編、上線自動合併（以時間戳 + 使用者為準，衝突時提示）。
4. 審核：editor 送審 → owner 在 UI 核准 → 後端用 GitHub App token 代為 commit / merge。使用者本人不需要有 repo 寫入權。
5. 稽核紀錄：誰、何時、改了哪頁哪個欄位，存 D1。
6. Token 管理：GitHub installation token 由後端持有並自動更新，前端永遠不再碰 token。這是相對純前端版最大的安全改善。

**資料表草案**（對照 Pages CMS）
```
users(id, email, github_id, name, created_at)
workspaces(id, name, slug, created_at)
memberships(user_id, workspace_id, role)
repos(id, workspace_id, github_installation_id, owner, name, default_branch)
drafts(id, repo_id, user_id, path, content_html, base_sha, updated_at)
reviews(id, draft_id, status, reviewer_id, pr_number, decided_at)
audit_log(id, workspace_id, user_id, action, target, payload_json, created_at)
```

**保留純前端版**：把現在的版本留作「離線版 / 自架版」入口，上雲版是同一份前端加上 `VITE_API_BASE` 就切換。不要分叉成兩個 codebase。

交付物：v5.0 beta，先開放給兩個已驗證過的實驗室（sung-lab、ycho-lab）試用。

### Phase 3：多租戶 SaaS（MVP 驗證後再決定）

只列方向，不排時程：
1. **代管網站**：使用者不需要 GitHub，網站直接存 R2 並由 Cloudflare Pages / Workers Sites 提供服務；GitHub 變成可選的「匯出 / 備份」。
2. **自訂網域**：Cloudflare for SaaS 的 custom hostnames。
3. **模板市集**：把 Greene Lab LWT 等模板預先轉成可編輯的靜態 HTML，一鍵建站。
4. **計費**：免費（1 個工作區、1 個網站）/ 實驗室方案（多網站、多成員、審核）。對照 CloudCannon 的定價區間定位在它的三分之一以下，主打台灣 / 亞洲學術單位。
5. **合規**：學術單位常問的資料落地問題，Cloudflare 可指定亞太區；若有需要再評估自架版授權。

## 四、系統架構演進（文字版）

```
Phase 0-1（現在）
  瀏覽器 (React) ──GitHub REST/GraphQL──▶ GitHub repo ──Actions──▶ GitHub Pages
        │
        └──OAuth code──▶ Cloudflare Worker ──▶ 換 token 回瀏覽器

Phase 2（上雲 MVP）
  瀏覽器 (React) ──HTTPS──▶ Hono on Workers ──▶ D1 / R2 / KV
                                   │
                                   └──GitHub App installation token──▶ GitHub repo ──▶ Pages
  （前端不再持有任何 GitHub token）

Phase 3（SaaS）
  瀏覽器 ──▶ Workers API ──▶ D1 / R2
                  │
                  ├──▶ R2 靜態站 ──▶ Cloudflare Pages / custom hostname（代管）
                  └──▶ GitHub（可選匯出）
```

## 五、主要風險與對策

| 風險 | 對策 |
|---|---|
| 加後端後失去「零設定、改原檔」的核心價值 | 每個 Phase 都保留純前端入口；round-trip 逐字元測試維持為 CI 必過項目 |
| GitHub API 速率限制（多人同時編輯） | Phase 2 由後端用 installation token 集中呼叫並以 KV 快取；讀取改走 GraphQL 批次 |
| 非你自己寫的 HTML 結構解析失敗（例如 `<section>` 不在 `<body>` 直屬） | Phase 0 就用 Greene Lab 等外部模板擴充語料；解析失敗時退回「唯讀 + 提示」而非崩潰 |
| Cloudflare D1 尚屬新產品，功能與工具鏈變動 | schema 用 Drizzle 抽象，必要時可換 Postgres；避免使用 D1 專有功能 |
| 研究室成員不會用 GitHub、不理解 PR | Phase 2 的 Email 登入 + 審核 UI 就是為此設計；PR 對使用者隱藏，只顯示「送審 / 已發布」 |
| 一人專案的維護量 | Phase 1 之前不要加後端；每個 Phase 結束都要有 tag 與可獨立運作的版本 |

## 六、本週可以直接動手的事

1. 在 `worker/` 加 `ALLOWED_DOMAINS` 與 `state` 檢查（半天）。
2. 建一個 `labsite-e2e-fixture` 測試 repo，寫第一個「登入 → 改欄位 → commit」的端到端測試（一天）。
3. 把 Greene Lab LWT clone 下來 `bundle exec jekyll build`，把 `_site/*.html` 丟進 round-trip 測試看結果（半天）。
4. README 加差異化段落與 `docs/markup-convention.md`（半天）。
5. 開一個 GitHub Project 看板，把本文件 Phase 0 / 1 的項目拆成 issue。
